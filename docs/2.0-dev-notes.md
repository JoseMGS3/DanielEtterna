# DanielEtterna 2.0 development — chart normalization

This branch starts from the current main branch. Its first milestone only
prepares chart input for XDC1. The 1.1.1 runtime and calculator have **not**
been replaced; the app is still labeled 1.1.1 until the full migration.

## Common note format

New API in src/chart_loader.py:

    data = chart_loader.load_chart_file(path)
    selected = ...  # existing UI chart selection for .sm/.ssc
    notes = chart_loader.normalize_chart_notes(data, selected)
    rated_notes = chart_loader.rate_normalized_notes(
        notes, rate=1.25, include_long_notes=True
    )

For .osu, omit the selected chart argument.

Every note is a triple of integer milliseconds:

    (column, start_ms, end_ms)

- column: 0, 1, 2, 3 (4 keys only)
- start_ms: absolute song time at original 1.0x rate
- end_ms: hold/roll release, or -1 for a tap
- Both start and end are scaled by rate with floor(), as expected by XDC1.
- The LN toggle can set end_ms to -1 without changing a chart's source.
- Rows are sorted by (start_ms, column).
- Negative start times due to OFFSET are preserved rather than clipped.
  The future XDC1 subprocess adapter must shift **all** times so that
  XDC1 receives nonnegative note heads, and restore the time axis later.
  A real hold end equal to -1 ms is explicitly rejected, to avoid being
  mistaken for a tap. The same guard exists after rate scaling.

## Format-specific rules

- .osu: reconstructs holds from the parsed object type 128, preserving
  the existing data["notes"] array of two-field tuples for 1.1.1.
- .sm: pairs type 2 (hold head) and type 4 (roll head) with type 3
  (release) in the same column, including across measure boundaries.
- .ssc: follows the same note rules but uses the **selected chart's**
  effective BPMs, STOPS, DELAYS, WARPS and OFFSET overrides.
- Type M (mine), L (lift), F (fake) are not modeled as playable
  keystrokes by XDC1 and are ignored. Unrecognized symbols fail explicitly.
- Orphan or unclosed holds, overlapping holds and malformed rows fail
  instead of silently contributing inaccurate difficulty estimates.
- Timing supports BPMS, STOPS, DELAYS and OFFSET through the existing
  beat-to-seconds converter. WARPS are still **not supported** and
  raise NotImplementedError instead of estimating the timing.
- All StepMania measures currently assume four beats, as before.
  Nonstandard time signatures are a separate future parser task.

## Backward compatibility

The existing convert_stepmania_chart() and load_osu()["notes"] paths
still produce (column, start_ms) pairs for the old calculator. This
change does not affect the normal UI, bridge polling, difficulty,
nomenclature labels or image assets.

## Milestone A complete: native XDC1 engine and Python adapter

- Upstream C++ source: xdc1/xdc1.cpp, copied without algorithm changes
  from TheBagelOfMan/xdc1 commit bc27ad77c1f94ddd871e9fba47ac69f56834da62.
- xdc1/LICENSE preserves its MIT copyright and redistribution notice.
- src/dan_scale.py is the original Daniel 2.x points-to-Dan calibration.
- src/xdc1_adapter.py accepts 4K triples, runs XDC1 with --graph through
  a subprocess, checks JSON/error handling, restores negative time-axis
  offsets, and returns the same calibration and seven skillsets as Daniel 2.x.
- The adapter is **not connected to src/daniel_etterna.py** yet; this
  deliberately leaves the current 1.1.1 app, bridge and UI unchanged.
- The engine output is not yet packaged inside the regular .exe build;
  packaging is deferred until the new UI path is ready.

### Python interface (for the next development phase)

    import chart_loader
    import xdc1_adapter

    data = chart_loader.load_chart_file("song.ssc")
    selected = data["charts"][0]  # replace with Etterna's selected chart
    result = xdc1_adapter.analyze_chart(
        data, selected, rate=1.0, include_long_notes=True
    )
    dan = result["rating"]
    skillsets = result["skillsets"]
    grid_ms = result["grid"]
    strain = result["strain_rested"]

The adapter accepts integer millisecond triples; it uses the native
engine's graph strain rather than changing the existing graph renderer.

## Experimental engine selector in Options > General

The difficulty-engine section is an expandable accordion below Keybinds.
It provides Legacy (default) and XDC1, with localized English/Spanish
descriptions. General is scrollable so expanded settings cannot obscure
Save/Cancel on smaller windows.

- Engine selection is persisted under difficulty_engine in config.json
  (config version 9); existing 1.1.1 configurations migrate to Legacy.
- Save applies the new engine for the same selected song. Cancel does not.
- XDC1 selection requires an installed/compiled binary; Save reports a
  localized error if the engine cannot be found.
- The Legacy path remains algorithm.calculate_notes(...) and Etterna's
  native MSD. XDC1 uses chart_loader.normalize_chart_notes(...), applies
  the live Etterna rate, executes the native engine, converts results to
  original Daniel 2.x Dan boundaries, and preserves Skins/DP/badge
  formatting. The statistics row uses XDC1's seven skillsets and does
  not label their ratings as Etterna MSD.
- The existing strain graph is reused with proximity fade and smoothing.
  This requires chart-specific in-game validation before releasing 2.0.
- WARPS, nonstandard time signatures, and other parser limitations
  remain unsupported in the new engine; Legacy behavior is unchanged.
- XDC1 is presently enabled for development testing; the application
  retains version 1.1.1 until release validation.

## Phase B — Etterna bridge and XDC1 graph integration

Module: src/etterna_xdc1_pipeline.py. It is GUI-independent and owns
three responsibilities:

1. Select the unique 4K dance-single chart from Etterna's bridge metadata
   (StepsType, difficulty, meter, optional description). If multiple SSC
   charts share difficulty/meter and the description cannot disambiguate,
   report no selected chart rather than rate the wrong one. The existing
   find_selected_sm_chart() delegates to this helper for both engines.
2. Convert the selected .osu/.sm/.ssc chart to 4K long-note triples,
   apply the Etterna playback rate to heads and tails, invoke XDC1,
   and produce the existing FastGraph-compatible time and strain arrays.
   The graph uses the upstream Daniel 2.x proximity fade and smoothing;
   no additional difficulty calculation is introduced by the smoothing.
3. Select the relevant XDC1 skillsets on their raw scale, reproducing
   upstream Daniel 2.x's 20% threshold and always retaining the strongest
   skillset. The Statistics/Full row is labeled in Dan, not MSD.

### Playback time alignment

Both menu and gameplay Lua bridges provide the song's original position
in milliseconds and the active playback rate. The chart calculation uses
t_note / rate, and the graph cursor uses:

    chart_ms = song_clock_ms / rate + elapsed_since_bridge_sample_ms

Both XDC1 and Legacy therefore use the same rated-time domain.
A missing, NaN, infinite, zero or negative rate is normalized to 1x;
nonfinite bridge song positions are discarded. This guards the Tk timer
against malformed or partially-written Lua bridge state.

### Chart switching and reentrancy

The calculation snapshot now includes the file, difficulty, meter,
description, StepsType, rate, and selected engine. The subprocess may
take longer than a single Etterna update. The result is discarded if
the chart, playback rate, engine, or connection phase has changed.
Queued Tk callbacks check the snapshot again before drawing the graph
and Dan. Saving a different engine resets cached results so the old
engine's strain/skillset values cannot be shown as the new engine.

### Tests and status

The GitHub workflow compiles the native XDC1 source and runs the entire
regression suite on both Linux and Windows. It also verifies selected
StepMania charts (including duplicate SSC difficulties, split timing,
holds and rate changes), the seven skillsets, normalization, and

## Debug console and diagnostics (opt-in)

The regular Windows binary uses --windowed and does not show a debug
terminal. To create a second EXE with a real console:

    build_debug_windows.bat
    dist\DanielEtterna-Debug.exe

This leaves dist\DanielEtterna.exe unchanged. Visual Studio C++ Build
Tools are required for either build because both package XDC1.

From an installed Python environment you can run instead:

    run_debug.bat

or:

    py src\daniel_etterna.py --debug

Debug mode writes a fresh session log to:

    %LOCALAPPDATA%\DanielEtterna\debug.log

The log contains chart filenames, difficulty, playback rates, note counts,
rating, processing duration, graph points, relevant skillsets, bridge
sample age and cursor position, and error tracebacks. It does not
record note sequences or keystrokes. The previous session's debug.log
is overwritten when debug mode starts. The normal GUI build does not
write this diagnostic log.

The debug report shows:
- Engine and Ready/error state, filename/difficulty/rate/4 keys
- Real 4K tap/hold/roll head counts for the selected chart
- Calculation timing vs total parsing + calculation timing
- Calibrated XDC1 Dan or separate Legacy SR (star scale)
- Graph point count and relevant XDC1 skillset names
- Bridge status (Gameplay, Menu/Preview, or stale), age, both rates,
  cursor position and rated graph time range
- "Rate aligned (visual synchronization NOT verified)" when both
  bridge/selected chart rates match and the sample is fresh
- Complete exception tracebacks when chart or XDC1 calculation fails

Every 8 seconds, a compact bridge-health report helps to distinguish
menu/playback/rate issues. This checks clock/rate metadata; it cannot
automatically prove that the painted cursor matches the game visually.

When you manually calculate the SAME chart at the SAME rate in
Legacy and then XDC1 (or vice versa), a comparison is printed. It
does NOT run both engines automatically, and it does not subtract the
different ratings because Legacy SR and XDC1 Dan use different scales.

### Recommended manual debug checks before release

1. Open an .ssc with taps, holds and rolls; verify the head counts
   and make sure tails aren't counted as extra taps.
2. Set Legacy at 1.0x, then XDC1 at 1.0x on the SAME selected chart;
   verify the Engine Comparison block and that the chart/rate match.
3. Try rates 0.75x, 1.0x, 1.25x and 1.5x, using both song preview and
   gameplay; verify the graph cursor visually in both modes.
4. Switch quickly between different difficulties/maps while XDC1
   computes; ensure the latest chart wins and no stale graph appears.
5. Verify an LN-heavy chart and a plain rice chart under XDC1;
   check whether the seven skillsets and curve make sense.
6. Switch among all five nomenclature presets and check the Images
   badge after changing the engine.
7. Choose a WARPS chart to observe the expected unsupported-timing
   error (no fabricated rating). Also verify disconnected/paused
   bridges show Waiting/Stale, rather than a fake "sync OK".
8. If anything fails, share the debug.log's relevant section, the
   selected chart format/rate, and a screenshot of the curve. Remove
   any private filenames/paths you don't wish to share.


## Phase C — graph identity and Dan classification

What is the "new" graph? The existing Full-layout FastGraph rendering is
reused. The visual style, accent coloring, and played/unplayed shading stay
unchanged. Only the underlying strain series changes with the engine:

- Legacy: algorithm.calculate_notes(...) time/strain arrays.
- XDC1: xdc1_adapter --graph strain_rested, after proximity envelope
  and smoothing inherited from Daniel 2.x. The smoothing does NOT change
  XDC1's numerical Dan rating or skillsets.
- Both use rated-time timestamps (song clock divided by rate). The
  renderer handles only visualization and the position split.

The Full graph no longer draws a strain/rate text caption, to keep the
overlay clean. The underlying strain data still switches with the selected
engine. The Statistics/Full skillset line keeps its skillset names,
and LN status but no longer prefixes the line with "XDC1".
In Settings, engine names and the technical availability hint remain;
the per-engine descriptions under each radio choice have been removed.

Dan classification in Phase C retains the original engine-specific
mapping: XDC1's calibrated rating goes through Daniel 2.x mean tiers;
Legacy retains its own original boundaries. Both can apply all five
editable nomenclature schemes to the resulting numeric DP without
changing their saved JSON files or any Images badge assets. No Dan
threshold or algorithm values were changed in Phase C.

Tests in tests/test_phase_c_display.py check the absence of the graph
caption, all mean/tier Dan boundaries, numeric continuity, five
nomenclature schemes and alpha/beta/kappa image badge names. Engine
settings tests verify the description-free radio selector.

## Optional XDC1 WASD column grouping (2.0-dev)

XDC1 continues to assume two fingers per hand. The **Standard** layout
retains the original left-hand columns 1-2 and right-hand columns 3-4.
The optional **WASD** layout only swaps physical columns 2 and 3 before
invoking the unchanged XDC1 engine, producing these internal groups:

- Standard: left 1-2, right 3-4
- WASD: left 1-3, right 2-4

The swap is zero-based `(0, 2, 1, 3)`; note times and LN tails are
unmodified and the source chart is never rewritten. All XDC1 scoring
coefficients, Dan thresholds, LN handling and skillset logic stay the
same. It changes how the engine attributes presses to the two hands,
so ratings can differ; **WASD is not separately calibrated**.

Use Options > Difficulty engine > XDC1 > Column layout to switch between
Standard and WASD. The profile is saved as `xdc1_column_layout` (default
`standard`, including existing installations), and switching it
recalculates the current chart. Legacy ignores this preference entirely.

Tests cover remapping and reverse mapping, LN/rate preservation,
adapter parity with the compiled native engine, configuration
persistence, and settings dispatch. Validate both layouts with live
Etterna gameplay before a 2.0 release.


## SM/SSC XDC1 millisecond parity with osu!mania

The XDC1 chart normalization path truncates computed SM/SSC note timestamps
using `floor(milliseconds + 1e-7)` instead of Python's `round()`.
The epsilon is expressed in **milliseconds** and only cancels microscopic
floating-point underflow at mathematically integral times. Example: at
160 BPM with StepMania `OFFSET=-0.400`, beats 2.5, 4.5 and 42 produce
osu!-compatible 1337, 2087 and 16150 ms respectively. LN tails use the
same conversion. The original **Legacy** calculator continues receiving
its unrounded floating-point times.

Verified locally against the user's Jack Dumps comparison (1708 notes,
3 LNs): after correcting that converted file's *own* `#OFFSET` from
`-0.477` to `-0.400`, the new conversion matches all 1708 original
osu! hit objects (including LN ends); the previous nearest-millisecond
conversion matched only 1207. The software does **not** infer or change
arbitrary `#OFFSET` fields: a genuine musical sync offset should be
preserved, and different timings legitimately produce different ratings.

Synthetic regression tests cover .osu/.sm note and LN parity, .ssc
per-chart timing, floating-point near-integer stability, and unchanged
Legacy timestamps. XDC1 engine formulas and Dan calibration are unchanged.
